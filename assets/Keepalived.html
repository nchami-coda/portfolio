Haute disponibilité de passerelle avec Keepalived et VRRP

Objectif : assurer la continuité d’accès à l’adresse d’un service même en cas de panne du routeur principal.

Contexte

Dans les infrastructures que j’ai mises en place jusqu’ici, chaque VLAN dispose d’une passerelle unique. C’est simple à administrer, mais cela crée un point de défaillance : si l’équipement tombe, tout le réseau perd son accès, même si les serveurs et les postes fonctionnent parfaitement.

Le problème posé : comment faire pour que la panne d’un routeur reste invisible pour les utilisateurs, sans avoir à reconfigurer manuellement la passerelle sur chaque poste ?

La réponse retenue : deux routeurs Debian partagent une même adresse IP virtuelle grâce au protocole VRRP. Les postes clients pointent vers cette adresse virtuelle et ignorent totalement lequel des deux routeurs la porte à un instant donné. En cas de panne du maître, le second reprend l’adresse en une seconde.

1. Rôle de Keepalived

  • Publie une adresse IP virtuelle (VIP) partagée entre plusieurs routeurs.
  • S’appuie sur le protocole VRRP (Virtual Router Redundancy Protocol).
  • Assure une bascule automatique si le routeur principal n’est plus joignable.

2. Installation de Keepalived (Debian)

sudo apt update && sudo apt upgrade -y
sudo apt install keepalived -y

# Vérifier l’installation
keepalived --version
sudo systemctl status keepalived

3. Configuration réseau préalable

Exemple d’adressage sur deux routeurs :

  • routeur1 : 192.168.20.10/24
  • routeur2 : 192.168.20.20/24
  • VIP : 192.168.20.30/24
  • Passerelle pour les clients : 192.168.20.30

Activer le routage IPv4 :

sudo nano /etc/sysctl.conf
net.ipv4.ip_forward=1
sudo sysctl -p

4. Exemple de configuration Keepalived

sudo nano /etc/keepalived/keepalived.conf

vrrp_instance VI_1 {
  state MASTER            # BACKUP sur le second nœud
  interface ens33         # adapter à l’interface réseau
  virtual_router_id 51
  priority 150            # 100 sur le nœud backup
  advert_int 1
  authentication {
    auth_type PASS
    auth_pass <secret_vrrp>
  }
  virtual_ipaddress {
    192.168.20.30/24
  }
}

Redémarrer le service pour appliquer les changements :

sudo systemctl restart keepalived
sudo systemctl enable keepalived

5. Tests de bascule

  • Depuis un poste client, ping 192.168.20.30 pour vérifier la VIP.
  • Simuler une panne du maître (sudo systemctl stop keepalived) et vérifier la continuité du ping.
  • Relancer le service et confirmer le retour automatique du maître (ip a pour visualiser la VIP).

Astuce : ajouter un track_script pour surveiller un service critique (ex. nginx) et déclencher la bascule si le service est indisponible.

Ce que ce TP démontre

  • Comprendre un point de défaillance unique et savoir le supprimer sans tout redéployer.
  • Le principe de l’adresse virtuelle, que l’on retrouve derrière la plupart des architectures redondantes (pare-feu en cluster, répartiteurs de charge, passerelles opérateur).
  • Valider une bascule par le test : couper volontairement le service maître et vérifier qu’un ping continu ne perd pas de paquet, plutôt que de supposer que la configuration fonctionne.
  • Aller plus loin avec track_script : faire dépendre la bascule de l’état réel d’un service, et non seulement de la disponibilité du système.

C’est le prolongement logique des missions GSB : la mission 2 rend le réseau fonctionnel, ce TP le rend tolérant à une panne.
